## 备注
- 发现：electron-vite dev 的文件监视在本次会话未触发主进程自动重启（疑为 Windows 文件监视或长驻会话原因），改为主进程代码变更后手动重启 dev 进程。后续阶段如遇「改了主进程代码没生效」，先重启 npm run dev
- 停掉 `npm run dev` 时务必确认端口 5173 已释放（TaskStop 只杀 npm，vite 子进程可能残留）——本日验证时改用 `netstat` 查 PID + `taskkill` 兜底
- 「无测试框架」的替代验证方式：临时写 `src/main/selftest.ts`（SELFTEST 环境变量触发，用 webContents.executeJavaScript 驱动真实界面点击/输入）→ 验证完删除。阶段 3 起继续沿用此法，比人工点一遍可靠
- 阶段 2 起主页点卡片进入的是**编辑器**（详情页在阶段 4 才有）；「我的」页目前是占位，阶段 5 完成
- **无 API Key 也能试玩**：`node scripts/mock-api.mjs` 起本地模拟接口（OpenAI 兼容，可模拟流式/401/404/400/慢速流），设置里填 `http://127.0.0.1:8787/v1` + `test-key-123` + `deepseek-chat`；`slow-model` 可体验「中途停止」——已用于阶段 3/4/5 的全部验证
- 界面自检教训：详情/聊天/设置页没有底部导航，脚本里点 `.tabbar-item` 前必须先回主页；检查项绝不能写死 `true`，必须用 waitUntil 的返回值
- 自检教训 2：不能用 Toast 文本当「保存完成」信号——上次保存的 Toast 会残留 2.5 秒造成误判，且保存响应回来后会覆盖表单、导致后续界面断言读到旧值。改为点保存后等固定时间直接读主进程状态
- 自检教训 3：校验逻辑在 IPC 边界（validateSettings），自检要验证它就必须走 `window.api.*` 真实路径，直接调 store 函数会绕过校验
- 自检教训 4：`webContents.executeJavaScript` 的返回值必须可序列化——注入「含函数的辅助对象」时脚本末尾要补一句 `true`，否则报 `An object could not be cloned`
- **端口 8787 上有上个会话残留的 node（mock-api）进程杀不掉**（`taskkill`/`Stop-Process` 都拒绝访问，父进程 29900），本次自检改用 `node scripts/mock-api.mjs 8788`；该残留进程重启电脑或注销后会自动消失，届时 8787 恢复可用
